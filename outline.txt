Project: a distributed core-banking platform (call it something like Ledgerline or Meridian Bank — name it once you start building)

The pitch: a small but architecturally real digital bank — not a demo, a system. Customers manage accounts and move money; bank staff monitor transactions and investigate flags; every action is provably auditable. The point isn't feature count, it's that every hard part of "real banking software" is actually solved, not simulated.

Two user roles, two experiences:

Customer — the dashboard we just mockup'd: account balances, transaction history, transfers, deposit/withdrawal.
Compliance/teller staff — a separate gated view: cross-account monitoring, flagged-transaction queue, audit trail search. This is the view that proves the RBAC work is real, not decorative.

Four backend services, talking over Kafka, not direct calls:

Account service — owns identity-to-account mapping, balances as a read-projection (never the source of truth).
Ledger service — the actual source of truth. Double-entry: every transaction writes a paired debit/credit, the system enforces they always net to zero. Concurrency-safe transfers via row-level or optimistic locking, so two simultaneous withdrawals can't double-spend.
Payment orchestration service — handles the multi-step transfer/payment flow as a saga (hold funds → validate → post → confirm, with compensating rollback on failure), and idempotency keys so a retried request never double-processes.
Audit & fraud service (your addition, not from either course) — an append-only log of every read/write on every account, plus a lightweight rules engine scoring transactions for velocity or amount anomalies.

Identity & security: Auth0 for authentication (JWT-based, both user-facing and service-to-service), role-based authorization gating what each service exposes to whom.

Frontend: React SPA talking to an API gateway, JWT-authenticated, with the two role-specific views above.

Delivery pipeline: everything Dockerized, GitHub Actions running tests and building images on every commit, deployed to AWS (EC2 or EKS), S3 for document/statement storage, SMTP for transaction and security notifications. This is a real CI/CD pipeline you can point to, not "I ran it locally."

What actually gets demoed in an interview:

A live URL, not just a GitHub link
A transfer that visibly triggers ledger entries, a Kafka event, an audit log line, and an email notification, end to end
A README opening with the architecture diagram, explaining why double-entry and concurrency locking exist, not just that they do

What it replaces on your resume: the three CRUD apps collapse into one line — a distributed banking platform with ledger integrity, event-driven orchestration, RBAC, and audit logging, deployed via CI/CD on AWS. That's the sentence that gets you past the resume screen at the DMV shops that actually build this kind of software for a living.

Phase 2 — Concurrency-Safe Transfers
Add locking to the transfer path — pick one:
Optimistic: version column on account/ledger rows, retry on conflict.
Pessimistic: SELECT ... FOR UPDATE on both accounts, always locked in a consistent order (e.g. lower account ID first) to avoid deadlock.
Write an integration test that fires many concurrent transfer requests at the same account and asserts the ending balance is exactly correct with zero lost updates. Run it repeatedly, not once.

Checkpoint: concurrency test passes reliably across 10+ runs; you can explain why the chosen locking strategy prevents double-spending.

Source: Custom — do this before building anything further on top of the ledger.

Phase 3 — Kafka Event-Driven Wiring
Kafka producers/consumers per Course A's pattern.
account-service publishes account-created / balance-changed events.
ledger-service publishes transaction-posted events.
Services consume relevant events to keep their own read models in sync — no direct service-to-service REST calls for this.

Checkpoint: kill and restart one service while the other runs — events queue in Kafka and process on reconnect with no data loss.

Source: Course A.

Phase 4 — Auth0 + JWT + Role-Based Authorization
Configure Auth0 as identity provider; issue JWTs with a role claim (customer or compliance_staff).
Implement JWT auth for user-facing requests and service-to-service calls.
Gate every endpoint by role at the Spring Security filter level — not just hidden in a UI.
Test: hit a compliance-only endpoint with a customer-role token and confirm a 403.

Checkpoint: two auth test collections (customer token, compliance token) — each correctly allowed/denied on every endpoint.

Source: Course A (auth setup) + custom (the enforcement test).

Phase 5 — Idempotency Keys
Require a unique client-generated idempotency key on every transfer/payment request.
Persist processed keys with their result; a repeated key returns the original result instead of re-executing.
Test: submit the identical request twice with the same key, assert money only moved once.

Checkpoint: duplicate-submission test passes.

Source: Custom.

Phase 6 — Payment Orchestration Saga

Build a dedicated payment-orchestration-service coordinating transfers as an explicit multi-step saga:

Hold — reserve funds on the source account without debiting.
Validate — run fraud/business-rule checks (wired to Phase 9 once it exists).
Post — write the atomic debit/credit pair to the ledger.
Confirm — release the hold, mark saga complete.
Compensate — on failure at any step, release the hold and mark failed, leaving no partial state.
Persist saga state (HELD, VALIDATING, POSTED, CONFIRMED, FAILED, COMPENSATED) so a crashed saga can be recovered or reconciled.
Test: force a mid-saga failure, assert the hold was released and no ledger entry exists.

Checkpoint: happy-path saga test passes end to end; failure-path test proves compensation actually reverses state.

Source: Custom — the largest net-new piece.

Phase 7 — React Frontend (Customer View)
Build the SPA: account dashboard, balances, transaction history.
Deposit, withdrawal, and transfer forms wired to the backend APIs.
Connect to the secured backend using the JWT auth pattern.

Checkpoint: customer can log in, view balances/history, and complete a transfer end to end through the UI.

Source: Course B.

Phase 8 — Dual-Role Frontend: Compliance View + Server-Side Enforcement
Add a separate compliance route/section: cross-account monitoring, flagged-transaction queue, audit trail search.
Gate it client-side (hidden from customer-role users) and server-side (a tampered customer JWT hitting a compliance endpoint still gets 403, per Phase 4).
Test: manually alter a JWT client-side to try to reach the compliance view — confirm the backend still rejects it.

Checkpoint: logging in as each role shows a genuinely different app; client-side tampering doesn't bypass server enforcement.

Source: Custom, extending Course B's frontend.

Phase 9 — Audit & Fraud Service
New service, append-only audit log: every read/write on every account writes an entry.
Hash-chaining — each entry stores a hash of the previous entry's content, so retroactive edits break the chain. Write a verification job that walks the chain and reports the first broken link.
Fraud rules engine — velocity check (too many transactions in a window) and amount-anomaly check (transaction far outside historical range).
Flagged transactions surface in the Phase 8 compliance queue.

Checkpoint: tampering with one row directly in the database is caught by the chain-verification job at the exact point of tampering; test fraud rules trigger correctly on crafted data.

Source: Custom — your original addition, not from either course.

Phase 10 — Wire Fraud Validation into the Saga
Connect Phase 6's "Validate" step to Phase 9's fraud rules (synchronous call or a quick Kafka round-trip).
A transaction that trips a fraud rule gets held/flagged by the saga instead of posting, and appears in the compliance queue.

Checkpoint: a crafted fraud-triggering transaction is stopped by the saga and visible to compliance staff, not silently posted.

Source: Custom — closes the loop between orchestration and fraud detection.

Phase 11 — Containerization
Dockerfiles for each backend service and the React frontend.
docker-compose.yml bringing up all services, Kafka, Postgres, and the frontend with one command.

Checkpoint: fresh clone, one docker-compose up, full system runs locally.

Source: Course B.

Phase 12 — CI/CD Pipeline
GitHub Actions workflow: run tests (including Phase 2 concurrency and Phase 5 idempotency tests) → build images → push to registry → deploy.
Zero-downtime deployment pattern from Course B.

Checkpoint: a commit to main triggers the pipeline and deploys automatically; a failing test blocks deployment.

Source: Course B.

Phase 13 — Cloud Integration
AWS S3 for statement/document storage.
SMTP service for transaction and security email notifications.
Deploy via Docker Compose on a single EC2 instance for the live demo (cheaper and just as demonstrable as a running cluster).
